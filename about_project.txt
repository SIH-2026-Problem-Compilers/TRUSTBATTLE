AI-Driven Battlefield Information Integrity & Trust Assessment
1. The Problem We Are Solving

Modern military operations depend on many interconnected information sources such as UAVs, GNSS/INS, radar, cameras, ground sensors and communication systems to build a real-time picture of the battlefield.

The problem is that information coming from a sensor cannot always be assumed to be trustworthy.

Information can become unreliable because of:

GNSS spoofing
False-data injection
Replay/stale data
Communication/network anomalies
Sensor malfunction
Jamming/degraded signals
Physical decoys/deception
Conflicting observations from different sensors

The dangerous part is that a manipulated measurement can sometimes look completely legitimate.

For example:

A UAV's GPS says:

"I am at Location A."

But its IMU, visual information and movement history indicate:

"This position is physically inconsistent."

The system therefore needs to answer:

"Can we trust this particular observation right now?"

rather than simply:

"What did the sensor report?"

2. Real-World Motivation

This is not a hypothetical problem.

The U.S. Army has an explicit program called Ensuring Sensor Data Security and Integrity, focused on protecting sensor data and maintaining its integrity throughout the data lifecycle.

India's SANJAY Battlefield Surveillance System also integrates ground and aerial sensor inputs and processes them to confirm their veracity before creating a common surveillance picture.

GNSS spoofing has also been demonstrated in real military conflicts, including the Russia–Ukraine war, where false navigation information has been used against UAVs.

The U.S. Army has specifically discussed GPS spoofing producing incorrect position/timing information and has tested systems designed to detect GNSS jamming/spoofing.

There are also documented battlefield uses of decoys and electronic deception where sensors can provide technically valid observations that nevertheless lead to an incorrect battlefield interpretation.

Therefore, the broader problem is:

How can a military system determine whether information received from a sensor or data source is trustworthy before allowing it to significantly influence the operational picture?

3. Our Core Idea

We are NOT trying to build another normal sensor-fusion system.

We are proposing an additional Information Integrity Layer on top of sensor systems.

Instead of:

Sensor → Data → Fusion → Decision

we want:

Sensor → Data → Trust/Integrity Assessment → Fusion → Decision

The system continuously evaluates each observation using multiple independent forms of evidence.

5. Important Design Principle

We will separate:

SENSOR RELIABILITY

How reliable has this sensor/source historically been?

from:

OBSERVATION TRUST

How trustworthy is this particular measurement right now?

Example:

Drone GPS

Historical reliability = 94%

Current observation:
GPS/IMU conflict
GPS/visual conflict
Telemetry anomaly

Current observation trust = 31%

A normally reliable sensor can temporarily produce an unreliable observation.

This distinction will be central to our system.

7. Technical Approach

We should NOT start with one huge deep-learning model.

We will use a hybrid AI + physics + cybersecurity approach.

Layer 1 — Physics/Consistency Analysis

We calculate relationships between sensor values.

Examples:

position residual
velocity residual
acceleration consistency
heading consistency
trajectory deviation
timestamp consistency
GNSS vs IMU disagreement
sensor-to-sensor disagreement

Example:

GNSS says:
velocity = 120 km/h

IMU says:
velocity = 55 km/h

Historical maximum:
80 km/h

This becomes an anomaly feature.

This layer gives us interpretable evidence.

8. Layer 2 — ML Anomaly Detection

We feed the extracted features into anomaly-detection models.

First models to test:
Isolation Forest
One-Class SVM
Random Forest/XGBoost where labelled data is available
Autoencoder as a later experiment

For the MVP, start with:

Isolation Forest

because it works well for unsupervised anomaly detection and doesn't require a huge labelled military dataset.

The model should output something like:

Anomaly Score = 0.87
9. Layer 3 — Temporal Analysis

Sensor data is a time series.

For example:

t1 → position
t2 → position
t3 → position
t4 → position
t5 → position

A spoofing/replay/manipulation event may produce an abnormal temporal pattern.

Initially we can use:

rolling statistics
velocity/acceleration changes
time differences
sequence features

Later we can experiment with:

LSTM/GRU
temporal autoencoder
lightweight Transformer

Do NOT start with the Transformer.

First create a working baseline.

10. Layer 4 — Cyber/Network Analysis

Our cybersecurity member will generate/monitor simulated telemetry behaviour.

Features can include:

packet rate
packet inter-arrival time
packet loss
packet delay
sequence number behaviour
timestamp behaviour
source ID
communication frequency

The ML model detects unusual communication behaviour.

For example:

Normal:

packet interval:
20 ms
21 ms
19 ms
20 ms
21 ms

Possible anomaly:

20 ms
21 ms
19 ms
950 ms
20 ms
4 ms
21 ms

This doesn't automatically mean "attack".

It becomes evidence contributing to the integrity assessment.

11. Layer 5 — Cross-Sensor Consistency

This is one of the most important components.

We compare independent sources.

Example:

GNSS → Position A
IMU  → Position B
Camera → Environment C

Calculate how consistent they are.

Output:

Cross-sensor consistency = LOW

Again, we don't immediately label it an attack.

It simply tells the trust engine:

"Something about this observation is inconsistent."

12. Layer 6 — Observation Trust Engine

This is where everything comes together.

Input:

Physical consistency
Temporal consistency
Cross-sensor agreement
Network anomaly
Historical sensor reliability
Signal quality

Output:

Observation Trust = 0–100

For example:

Historical reliability       0.94
Physical consistency         0.25
Temporal consistency         0.42
Cross-sensor agreement       0.18
Network integrity            0.31

                  ↓

Observation Trust = 0.29

The exact weighting should be learned/experimentally validated rather than arbitrarily chosen.

We can initially use a weighted model and later train a supervised/ensemble model to learn the relationship.

14. Robust Fusion

Now we compare two systems.

Normal fusion

All sensors receive approximately equal/normal influence.

GNSS = 33%
IMU = 33%
Visual = 33%
Trust-aware fusion

Influence changes according to current observation trust.

GNSS = 10%
IMU = 45%
Visual = 45%

These numbers are only examples.

The actual fusion weights will come from our model.

The goal is:

When one information source becomes unreliable, the system should reduce its influence instead of allowing the corrupted information to dominate the final estimate.

16. Important: Don't claim the AI can prove an attack

Our system should NOT say:

"The sensor has been hacked."

unless we have sufficient evidence.

Instead:

"The observation is inconsistent/unreliable, with evidence potentially consistent with spoofing, malfunction or communication manipulation."

This is technically more correct.

Our system is primarily an:

Information Integrity / Trust Assessment System

not an:

Attack Attribution System

25. Research Hypothesis

We can formally test:

A multi-evidence observation-integrity model combining physical consistency, temporal behaviour, communication characteristics, historical reliability and cross-sensor agreement can identify unreliable sensor observations and reduce the impact of corrupted information on situational estimation compared with conventional sensor fusion.

This gives us an actual research question rather than just a product demo.
